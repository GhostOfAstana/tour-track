# Вопросы аудитора и объяснение реализации

Это справочник по устройству проекта, а не заявление об авторстве или гарантия отсутствия любых ошибок. Ответы опираются на код. На проверке текущие числа нужно брать из открытого каталога: внешний API и текущий год могут измениться.

## Пять основных вопросов из ТЗ

### 1. Как загружаются и связываются четыре части API?

Простыми словами: четыре ответа похожи на четыре таблицы. В первой находится сам артист, во второй — места, в третьей — даты, в четвёртой — соответствие места и дат. Поле `id` играет роль общего номера артиста. Положение строки в ответе значения не имеет.

Точно по коду:

1. `main.go` создаёт `catalog.Client` с адресом из `API_BASE_URL`. По умолчанию это адрес API из ТЗ.
2. `Client.Fetch` одновременно запускает четыре GET-запроса: `/artists`, `/locations`, `/dates`, `/relation`. Каждый запрос выполняется в своей горутине; результаты приходят через канал с буфером на четыре ответа.
3. Каждый ответ должен иметь HTTP 200, корректный JSON и размер не более 4 МиБ. После JSON не должно быть другого документа или посторонних данных.
4. `join` строит соответствие `id → позиция артиста`, затем добавляет поля остальных частей по этому номеру.
5. Перед выдачей каталога проверяются положительные уникальные номера артистов, непустые имена и наличие соответствующей записи во всех трёх остальных частях. Неизвестные или повторные номера и отсутствующие обязательные массивы/объекты отклоняются.
6. Только целый результат может заменить кеш. Если одна часть сломалась, посетители продолжают видеть предыдущий целый каталог.

Названия полей и их использование:

| Часть | Что используется | Где видно |
| --- | --- | --- |
| `artists` | Имя, изображение, участники, год начала карьеры, первый альбом | Главная и страница артиста |
| `locations` | Исходный список мест; из него выделяются страны | Список локаций, география и баллы |
| `dates` | Исходный список концертных дат | Список дат, общий счётчик и Rising Star |
| `relation` | Словарь `datesLocations`: место → даты | Таблица маршрута на странице артиста |

Ссылки, лежащие внутри JSON, не используются для дополнительных серверных запросов. Клиент обращается к четырём заранее известным путям настроенного API. Сортировка ключей `relation` делает порядок таблицы устойчивым: обход словаря Go сам по себе постоянного порядка не обещает.

Код: [клиент и связывание](../internal/catalog/client.go), [модель каталога](../internal/catalog/models.go).

### 2. Как данные превращаются в балл и метку? Что означает каждый член формулы?

Простыми словами: за каждую страну начисляются два балла, за каждую концертную дату — три. Длительность карьеры добавляет ещё немного баллов, но не больше десяти. Затем число попадает в один из четырёх диапазонов.

```text
score = tour_spread × 2 + concert_count × 3 + min(10, career_years / 5)
```

- `tour_spread` — количество разных стран, выделенных из `locations`.
- `concert_count` — длина списка `dates`.
- `career_years` — текущий год сервера минус `creationDate` артиста; отрицательный результат заменяется нулём.
- `/ 5` — целочисленное деление. Например, 24 года дают 4 балла за карьеру, 25 лет — 5.
- `min(10, …)` ограничивает вклад карьеры десятью баллами. Пятьдесят и сто лет дают одинаковый карьерный вклад.

| Балл | Метка |
| --- | --- |
| 0–10 включительно | Emerging |
| 11–25 включительно | Active |
| 26–40 включительно | Established |
| От 41 | Legendary |

Обязательный пример: страны `5`, даты `8`, карьера `30` лет.

```text
5 × 2 + 8 × 3 + min(10, 30 / 5)
= 10 + 24 + 6
= 40 → Established
```

Ровно 40 ещё не `Legendary`; эта метка начинается с 41. Ровно 25 относится к `Active`, а 26 — к `Established`.

Основная метка видна на каждой карточке главной страницы и на странице артиста. На странице артиста также показаны все исходные счётчики. Самостоятельная функция `Score` вычисляет число; `Classify` возвращает строковую метку; `Analyze` подготавливает счётчики из исходных данных.

Код: [internal/activity/classifier.go](../internal/activity/classifier.go).

### 3. Как вычисляются уникальные страны и продолжительность карьеры?

Простыми словами: несколько концертов в США означают одну страну. Год начала деятельности вычитается из текущего года, а не из года первого альбома.

`Countries` берёт часть локации после последнего дефиса. У `los_angeles-usa` это `usa`, у `new-city-new_zealand` — `new_zealand`. Последний дефис выбран потому, что дефис может быть и в названии города. Пробелы по краям удаляются, буквы приводятся к нижнему регистру, подчёркивания в названии страны превращаются в пробелы. Набор `map[string]struct{}` исключает повторы.

Небольшая явная таблица синонимов объединяет:

- `usa`, `united states`, `united states of america`;
- `uk`, `united kingdom`;
- `brasil`, `brazil`.

Другие названия произвольно не объединяются: например, `north korea` и `south korea` остаются разными странами. Строка без разделителя, без города или без страны не создаёт выдуманную страну. Результат сортируется для стабильного отображения.

Например, `los_angeles-usa`, `houston-usa`, `london-uk`, `sao_paulo-brasil`, `rio-brazil` дают три страны: `usa`, `uk`, `brazil`. Исходные локации при этом сохраняются в каталоге без исправлений.

Возраст карьеры определяется в `Analyze` по переданному `now.Year()` и `CreationDate`. В HTTP-обработчиках `now` берётся заново при запросе; обычная реализация — `time.Now`. При будущем годе начала карьеры результат равен нулю. В тестах часы подменяются, поэтому сценарий следующего года воспроизводится без изменения системного времени.

### 4. Почему текущий год вычисляется при запросе, а не записан в коде?

Простыми словами: артист становится старше по мере течения времени. Если зафиксировать год в коде или навсегда сохранить готовый балл, программа через год продолжит считать старую продолжительность карьеры.

Кеш хранит исходные данные артиста, а не готовую классификацию. Главная страница получает один момент времени для всего списка, затем заново вызывает `Analyze`. Страница одного артиста делает то же при своём запросе. Это соответствует требованию `time.Now().Year()` на момент обработки запроса и исключает разный год у двух карточек одного ответа на границе Нового года.

Для расчёта используется календарь и часовой пояс процесса сервера. Это не персональное время браузера посетителя. Время сохранения каталога отображается отдельно и явно в UTC. Оно не участвует в определении возраста карьеры.

Сам балл не обязан увеличиваться каждый год: карьерная часть растёт только раз в полные пять лет и перестаёт расти после десяти баллов.

### 5. Как выбрать артиста и предсказать метку вручную до проверки результата?

Сначала нужно взять исходные значения: год начала карьеры, список локаций и список дат. Затем посчитать разные страны, все записи дат, разницу лет и подставить их в формулу. Метка определяется только после сложения.

Для сохранённого исторического каталога пример на 2026 год:

| Артист | Страны | Даты | Год начала | Лет карьеры в 2026 | Расчёт | Предсказание |
| --- | --- | --- | --- | --- | --- | --- |
| Queen | 3 | 8 | 1970 | 56 | `3×2 + 8×3 + 10 = 40` | Established |
| Travis Scott | 6 | 12 | 2008 | 18 | `6×2 + 12×3 + 3 = 51` | Legendary |
| Gorillaz | 2 | 5 | 1998 | 28 | `2×2 + 5×3 + 5 = 24` | Active |
| Foo Fighters | 6 | 8 | 1994 | 32 | `6×2 + 8×3 + 6 = 42` | Legendary |

Эти числа относятся к встроенному архиву и указанному году. После успешного обновления живого API или смены года нужно пересчитать пример по текущим данным. Для проверки полного результата доступен JSON по `/api/artists/{id}`; в `activity` перечислены исходные счётчики, итог и метки.

## Вопросы о данных и классификаторе

### Это машинное обучение? Где модель и обучение?

Нет отдельной обученной модели. ТЗ называет AI правиловую классификацию: фиксированная формула и пороги. Это объяснимое эвристическое правило. Здесь нет обучения, нейросети, токенов, запросов к AI-сервисам или скрытых коэффициентов. Ограничение на стандартную библиотеку соблюдается и в этой части.

### Почему используется отдельный пакет `internal/activity`?

Чтобы расчёт можно было проверить без браузера, HTTP-сервера и интернета. Пакет получает данные и время, возвращает результат, не загружает API и не знает об HTML. `Score` и `Classify` можно вызвать независимо. Каталог, кеш, расчёт и отображение имеют разные обязанности.

### Что означает «число концертов»: уникальные дни или длина списка?

В реализации это `len(dates)`: количество записей дат из API, как требует общий счётчик ТЗ. Одинаковые даты не удаляются: в один день возможны разные выступления. Для общего балла учитываются также будущие и нераспознанные строки дат — это счётчик записей источника, а не проверенных состоявшихся событий.

Для Rising Star правила строже: строка должна успешно разбираться как календарная дата и попадать в недавнее окно. Нераспознанные строки считаются в `InvalidDates`, чтобы их можно было заметить. Предшествующая звёздочка `*` перед разбором снимается; исходный текст в интерфейсе сохраняется.

### Почему артист без концертов может получить баллы за карьеру?

Так задана формула. При нуле стран и нуле дат вклад карьеры не превышает 10, поэтому метка будет `Emerging`. «Мало концертов» не является отдельным условием: при большом количестве стран итог может попасть в следующий диапазон. Приоритет имеет точный числовой расчёт, а не субъективное впечатление от артиста.

### Что будет с отрицательными или чрезмерно большими числами?

Публичная функция `Score` заменяет отрицательные аргументы нулями. Сложение и умножение проверяются на переполнение; если математический результат больше диапазона `int`, возвращается максимальный `int`, а не отрицательное или случайно малое число. Метка при таком результате — `Legendary`.

Нормальный каталог ограничен размером API-ответов и до таких значений не доходит. Эти проверки полезны для прямого вызова функций и стресс-тестов. Разница лет также защищена от переполнения на экстремальных значениях.

### Не меняет ли программа имена из API ради аудита?

Имена, состав группы, первый альбом, исходные локации и даты сохраняются как пришли. Поэтому в Queen видны именно `John Daecon`, `Roger Meddows-Taylor`, `Doug Fogie` и другие написания учебного источника. Это не редактор музыкальной энциклопедии. Нормализация страны используется в отдельном расчёте и не переписывает исходный список локаций.

Проверки из ТЗ удобно выполнять поиском `Queen`, `Gorillaz`, `Travis Scott`, `Foo Fighters` и открытием страницы артиста. Для Gorillaz в архиве первый альбом — `26-03-2001`.

### Почему у Travis Scott написано `sao_paulo-brazil`, если в аудите ТЗ указано `sao_paulo-brasil`?

В сохранённых исходных JSON используется `sao_paulo-brazil`. В тексте аудита приведён вариант `sao_paulo-brasil`. При подготовке резерва три независимые публичные копии совпали по фактическим записям; подробности находятся в [PROVENANCE.md](../internal/seed/PROVENANCE.md).

Исходная строка не переписывается ради буквального совпадения с формулировкой аудита. На странице есть пояснение о двух написаниях Бразилии. В расчёте `brazil` и `brasil` нормализуются в одну страну, поэтому расхождение не меняет `tour_spread`, балл или метку. Это различие текста ТЗ и архива, а не две разные концертные локации.

## Бонус Rising Star

### Как точно работает правило ускорения?

Простыми словами: недавние концерты делятся на два года. Все концерты делятся на количество лет карьеры. Недавнее среднее должно превысить карьерное более чем на половину.

```text
recent_rate = recent_concerts / 2
career_rate = concert_count / career_years
Rising Star, если recent_rate > career_rate × 1,5
```

Для положительного стажа это равносильно сравнению:

```text
recent_concerts × career_years > concert_count × 3
```

`IsRisingStar` сравнивает целые произведения с помощью стандартного `math/big`. Поэтому нет округления дробей и переполнения на больших аргументах. Нулевой или отрицательный стаж, нулевое общее количество или отсутствие недавних концертов дают `false`.

### Проверяются ли примеры 7 против 4 и 5 против 4?

Да, в тестах есть оба примера. При `concert_count=40` и `career_years=10` карьерное среднее равно 4 концертам в год:

- 14 недавних дат дают 7 в год: `7 > 4×1,5`, метка есть;
- 10 недавних дат дают 5 в год: `5 > 6` неверно, метки нет;
- 12 недавних дат дают ровно 6 в год: превышение ровно на 50%, поэтому метки тоже нет;
- 13 недавних дат дают 6,5 в год: строгое условие выполнено.

### Что означает «последние два года»?

Это скользящее окно календарных дат: от сегодняшней даты минус два года до сегодняшнего дня включительно, а не два последних календарных года целиком. Например, на 7 ноября 2026 года включается 7 ноября 2024 года, но не 6 ноября 2024 года. 7 ноября 2026 года включается независимо от текущего часа; 8 ноября ещё находится в будущем и не включается.

Окно создаётся в часовом поясе переданного `now`. Используется календарное правило `time.AddDate(-2, 0, 0)`. Особенность Go: для 29 февраля 2024 года начало двухлетнего окна нормализуется в 1 марта 2022 года. Это поведение зафиксировано тестом, а не оставлено случайности.

### Почему на старом каталоге может вообще не быть Rising Star?

Старые концертные даты могут целиком находиться за пределами последних двух лет. Тогда недавний счётчик равен нулю и метка отсутствует. Даты не переносятся в будущее ради демонстрации бонуса. Правило проверяется на воспроизводимых тестовых данных; реальные карточки получают метку только при фактическом выполнении условия.

## Асинхронность, кеш и отказоустойчивость

### Какое действие демонстрирует client-server request-response?

Обычный поиск отправляет GET-запрос и получает страницу с результатами. Дополнительное интерактивное действие — «Обновить данные»: браузер отправляет POST `/api/refresh`, получает HTTP 202 и затем GET-запросами читает `/api/status`. После завершения успешного обновления страница загружается заново. При ошибке посетитель получает сообщение, а старый каталог остаётся на экране.

### Где именно горутины и каналы? Почему нажатия не запускают бесконечно много работ?

В `main.go` один фоновый работник вызывает `Store.Run`. Канал `queue` вмещает одно задание. Под блокировкой `RequestRefresh` проверяет флаг `refreshing`: повторные запросы присоединяются к уже поставленному или выполняемому обновлению. Для каждого клика новая рабочая горутина не создаётся.

Внутри одного обновления `Client.Fetch` запускает четыре горутины для четырёх частей API. Их канал результатов имеет буфер четыре. Даже если `Fetch` вернулся после первой ошибки, остальным горутинам есть куда отправить результат; общий контекст отменяет их сетевые запросы.

После завершения обновления действует пауза 10 секунд до начала следующего. Автоматический таймер предлагает обновление каждые пять минут. Таким образом, ограничено количество одновременных обращений приложения к внешнему API; это не глобальное ограничение всех входящих соединений HTTP-сервера.

### Почему страницы читают кеш, а не ходят в API при каждом открытии?

Это позволяет быстро открывать каталог и продолжать работу во время отказа внешнего сервиса. У посетителя нет четырёх новых сетевых зависимостей при просмотре каждой карточки. Текущие оценки при этом рассчитываются заново: кешируются исходные сведения, а не возраст карьеры и не готовый балл.

`sync.RWMutex` защищает публикацию и чтение снимка. При выдаче снимка копируются также вложенные списки участников, локаций, дат и связей. Обработчик не получает возможность случайно изменить внутренние данные кеша через общий срез.

### Что произойдёт, если API вернёт 404, 500, сломанный JSON или только три части?

Новое состояние не публикуется. Кеш сохраняет предыдущий полный каталог, отмечает его `Stale=true` и записывает общее сообщение `last_error`. Браузер видит предупреждение о неподтверждённых свежих данных. Код ошибки внешнего API не превращается автоматически в такой же код страницы: сохранённая страница остаётся полезным HTTP 200, но её состояние явно обозначено.

При запуске предусмотрен архивный резерв. Его происхождение описано в [PROVENANCE.md](../internal/seed/PROVENANCE.md). Он не выдаётся за успешный ответ работающего API. Если каталог пуст и получить данные не удалось, страница и данные артистов возвращают HTTP 503.

Проверка согласованности подтверждает структуру и общий набор `id`, но не доказывает фактическую истинность концертов или то, что четыре отдельных ответа были сделаны внешним сервисом в одну транзакцию.

| --- | --- | --- |
| HTTP-клиент API | 12 секунд по умолчанию | Не ждать источник бесконечно |
| Контекст одного обновления кеша | 12 секунд | Общий срок для загрузки |
| Один ответ API | Не более 4 МиБ | Ограничить чтение и разбор ответа |
| Заголовки входящего запроса | `ReadHeaderTimeout=5s`, `MaxHeaderBytes=16 KiB` | Ограничить ожидание заголовков и их размер |
| Чтение запроса | `ReadTimeout=10s` | Ограничить медленное чтение |
| Запись ответа | `WriteTimeout=20s` | Ограничить медленную отправку |
| Простой соединения | `IdleTimeout=60s` | Освобождать неиспользуемые соединения |
| Поисковая строка | Не более 200 символов | Ограничить пользовательский параметр |
| URI | Не более 4096 байт | Ограничить адрес запроса |
| Известная длина тела обновления | Более 1024 байт отклоняется | Действию не требуется большое тело |

Эти ограничения уменьшают влияние ожидаемых сбоев. Они не заменяют лимиты памяти, процессора, соединений и защиту хостинга.

### Как приложение останавливается?

При `SIGINT` или `SIGTERM` отменяется общий контекст, прекращаются фоновые операции и отменяются текущие обращения к API. `http.Server.Shutdown` получает отдельные 10 секунд на завершение текущих ответов. Если мягкая остановка не успевает, соединения закрываются принудительно. Ошибка запуска, например занятый порт или неверный `PORT`, сообщается в журнал, а процесс заканчивается с ошибкой.

## HTTP-методы, статусы и защита

### Какие маршруты нужны для проверки?

| Маршрут | Метод | Результат |
| --- | --- | --- |
| `/` | GET, HEAD | Каталог, поиск, фильтр, сортировка |
| `/artists/{id}` | GET, HEAD | Страница артиста |
| `/api/artists` | GET, HEAD | JSON каталога с вычисленными оценками |
| `/api/artists/{id}` | GET, HEAD | JSON одного артиста |
| `/api/refresh` | POST | Постановка или присоединение к обновлению |
| `/api/status` | GET, HEAD | Состояние обновления и сохранённого каталога |
| `/healthz` | GET, HEAD | Процесс отвечает на HTTP |
| `/readyz` | GET, HEAD | Есть ли каталог для обслуживания |
| `/static/style.css`, `/static/app.js` | GET, HEAD | Локальные стили и скрипт |

`HEAD` возвращает статус и заголовки без тела. Чтение сделано через GET, изменение состояния обновления — через POST. Другой метод получает HTTP 405 и заголовок `Allow`.

### Чем отличаются 404, 500, 503 и 429?

- **404**: неизвестный путь, статический файл или номер артиста. Это ожидаемый ответ на отсутствующий ресурс; требование «все страницы работают» не означает, что произвольный адрес обязан существовать.
- **500**: внутренняя ошибка приложения. Например, ошибка выполнения шаблона. Шаблон сначала полностью собирается в буфере, поэтому ошибочная половина страницы не успевает уйти как успешный ответ. Ошибка записывается в журнал; посетителю не показывается трассировка стека.
- **503**: нет каталога для обслуживания. `/readyz` в этом случае тоже отвечает 503.
- **429**: новое обновление запрошено до окончания десятисекундной паузы после предыдущего; указан `Retry-After: 10`. Повторное обращение во время уже выполняемой работы присоединяется к ней и получает 202.

Для HTML-маршрутов предусмотрена понятная страница ошибки со ссылкой на главную, для `/api/…` — JSON. Некорректные параметры дают 400, чужой браузерный источник обновления — 403, слишком большое тело, включая поток без объявленной длины — 413, длинный URI — 414.

### `/readyz` с кодом 200 доказывает доступность внешнего API?

Нет. Это означает, что в памяти есть каталог и приложение может обслужить посетителя, в том числе из резерва. Свежесть проверяется по `stale`, `updated_at` и `last_error` в `/api/status`. `/healthz` ещё проще: он показывает, что сам HTTP-обработчик отвечает.

### Как обрабатывается непредвиденная паника?

Входной HTTP-обработчик имеет `recover`, а вызов источника данных защищён отдельным `safeFetch`. Ожидаемые ошибки сети, JSON, маршрутов и параметров передаются обычным `error` или HTTP-статусом, а не паникой. После паники источника предыдущий каталог сохраняется; это проверяется тестом.

Это не математическая гарантия «процесс не может завершиться ни при каких обстоятельствах». Принудительное завершение ОС, исчерпание памяти, отказ машины и некоторые ошибки среды требуют защиты на уровне хостинга. Если часть ответа уже была отправлена, HTTP-статус задним числом изменить нельзя. В обычном рендеринге буферизация помогает не начинать ответ до успешной сборки страницы.

### Как предотвращается внедрение HTML или скрипта из API и поиска?

Для HTML используется `html/template`, который экранирует данные с учётом места вставки, включая текст, атрибуты и URL. Полученные строки не превращаются в `template.HTML` или другой доверенный исполняемый тип. В JavaScript сообщения задаются через `textContent`, а не `innerHTML`.

Дополнительно отправляется Content Security Policy: скрипты и стили только с самого сайта, inline-скрипты не разрешены, загрузка во фрейме запрещена, формы отправляются на этот же сайт. `X-Content-Type-Options: nosniff` ограничивает угадывание MIME-типа. Внешние HTTPS-изображения разрешены, потому что их адреса приходят из API; их загрузка происходит в браузере. Отказ изображения не мешает просмотру сведений артиста.

### Почему проверяется Origin у обновления?

Чтобы другой сайт не заставлял браузер посетителя запускать обновления. Для POST проверяется совпадение хоста `Origin` и допустимая схема; `Sec-Fetch-Site: cross-site` отклоняется. Сервер не имеет пользовательских учётных записей и не хранит пользовательские сессии. Такие проверки вместе с очередью и паузой ограничивают нежелательные браузерные запросы; это не обещание защититься от любого прямого клиента или DDoS.

## Стандартная библиотека, тесты и размещение

### Какие внешние Go-пакеты установлены?

Никакие. `go.mod` объявляет модуль и версию языка, без секции сторонних зависимостей. Сервер, JSON, HTML-шаблоны, HTTP-тесты, синхронизация, большие целые числа и встроенные файлы реализованы пакетами стандартной библиотеки Go. HTML, CSS и обычный браузерный JavaScript не требуют npm или CDN. Внешний API является источником данных, а не зависимостью Go-модуля.

Проверка списка модулей:

```sh
go list -m all
```

В текущем проекте ожидается только модуль `tour-track`.

### Зачем внедряются HTTP-клиент, источник и часы?

Чтобы тестировать сложные ситуации воспроизводимо. `httptest.Server` изображает API с нужным статусом, задержкой или повреждённым ответом. Интерфейс `cache.Fetcher` позволяет вернуть ошибку, панику или управляемый результат. Подменяемая функция `now` позволяет проверить новый год и точную границу десятисекундной паузы без долгих ожиданий.

Подход проверяет поведение на внешней границе, а не требует работающего интернета или изменения системного календаря.

### Какие тесты покрывают требования и отказы?

- `internal/activity`: формула, пороги 10/11/25/26/40/41, обязательный пример 40, страны и синонимы, ограничения стажа, отрицательные и предельные числа, правило Rising Star, границы скользящего окна, високосный год и нераспознанные даты.
- `internal/catalog`: связывание по `id`, параллельная загрузка четырёх частей, артист без концертов, некорректные или несогласованные снимки, HTTP-ошибки, отмена, тайм-аут и одновременные вызовы.
- `internal/cache`: 200 одновременных нажатий объединяются в одно задание; ошибка или паника источника сохраняет предыдущий каталог; вложенные срезы копируются; пауза проверяется до и на самой границе; отмена останавливает работу.
- `internal/web`: карточки и страницы проверяемых артистов, пересчёт оценки при новом запросе, поиск и сортировка, HTTP-методы, отсутствующие ресурсы, неправильные параметры, экранирование вредоносных строк, запрет чужого Origin, ограничение обновлений, HEAD, служебные маршруты, ошибка шаблона и 200 параллельных чтений без изменения кеша.
- Fuzz-тесты в `internal/activity` подают разные числа и повреждённые строки, проверяя устойчивые свойства: балл неотрицателен, добавление страны не уменьшает балл, анализ не должен паниковать на таких входах.

Присутствие теста и результат его последнего запуска — разные факты. Результат проверки конкретной версии следует фиксировать по фактическому выводу команд, а не по обещанию в документации.

### Как повторить проверки без установки сторонних инструментов?

В окружении с подходящей версией Go:

```sh
go test ./...
go test -race ./...
go vet ./...
```

Отдельные короткие fuzz-запуски:

```sh
go test ./internal/activity -run '^$' -fuzz '^FuzzScoreNeverBecomesNegative$' -fuzztime=10s -parallel=2
go test ./internal/activity -run '^$' -fuzz '^FuzzAnalyzeMalformedInput$' -fuzztime=10s -parallel=2
```

Race detector зависит от поддержки платформой и доступности требуемого системного инструментария. Он ищет гонки на выполненных путях, а не доказывает отсутствие любых ошибок конкурентности. Fuzz-проверка исследует входы за выделенное время и тоже не является исчерпывающим доказательством.

### Как проверить бонус публичного DNS?

Нужен фактически запущенный Go-сервис на хостинге и настоящий адрес, который открывается извне. Наличие Dockerfile, конфигурации развёртывания или имени домена в документации само по себе не выполняет этот бонус. У работающего размещения следует открыть главную, страницу артиста и `/healthz`, затем проверить событие обновления и предупреждение при недоступном API.

Этот справочник не утверждает, что размещение выполнено: адрес и результат развёртывания должны подтверждаться отдельно. Сервер умеет получать `PORT`, `HOST` и `API_BASE_URL` из окружения; для публикации он должен слушать интерфейс, доступный хостингу.
